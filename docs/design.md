# macOS 离线终端补全工具设计

日期：2026-11-10  
状态：设计提案，供项目实现使用  
项目名称：暂定 Offline Complete

## 1. 背景与目标

用户习惯 Kiro CLI 的终端命令补全，希望将这套体验独立成 macOS 应用，不依赖 Kiro、账号、云服务或在线规则。安装包包含规则；程序可以根据用户的实际选择，在本机逐步改善补全排序和发现可能缺失的选项。

### 必须满足

- 首次启动、日常运行、学习和配置均不需要互联网；不发送遥测，不自动更新。
- 提供输入时的候选弹窗、键盘选择、说明和插入，尽量接近现有体验。
- 基础命令规则及其运行所需资源随安装包提供，不从远端加载。
- 学习数据仅保存在本机，可查看、关闭、删除和撤销。
- 支持与现有 Kiro 共存的安装、停用和卸载；避免两个补全进程同时接管同一 shell。

### 不在第一版范围

- AI 对话、远程推理、账号登录、插件商店、云同步和自动更新。
- 自动执行用户正在编辑的命令；自动生成或修改项目文件。
- 根据少量输入自动改写共享基础规则，或承诺推导任意 CLI 的完整语法。
- 第一版支持 Linux、Windows 或所有终端模拟器。

## 2. 实现路线

**实现路线：以 Amazon Q Developer CLI Autocomplete 的公开实现、规则格式和终端行为为参考，用 Go 重写离线核心：PTY 会话代理、shell 集成、IPC、解析、规则、候选、排序与学习。** 不迁入 figterm 的 Rust 主循环，也不保留其认证、网络、更新和遥测路径。macOS 候选窗口如果必须依赖 AppKit，只允许窗口层使用 Swift/Objective-C，核心逻辑仍为 Go。先验证 macOS 构建、shell 接入和窗口定位，再逐模块实现。

备选方案是裁剪上游 Rust 代码以复用终端兼容逻辑：能更快得到可运行原型，但与“项目代码尽量使用 Go”的方向冲突，还需保留 Rust 工具链并做更复杂的许可审计，第一版不采用。完全从零实现终端会话成本最高，但 Go 生态已有可审计的 PTY 依赖，因此采用小模块重写而不是整包复用。

以上是设计建议，不是已经完成的技术验证。原仓库声明 MIT OR Apache-2.0；发布时选择适用许可证并保留必要声明，逐项核查第三方依赖、规则、字体、图标与商标。不要把线上 CDN 文件视为已获重新分发许可；无法确认许可的规则不打包。

## 3. 范围与默认决策

- 第一目标环境：macOS，优先 Apple Silicon 和 zsh；同时保留 Intel 构建能力。具体最低 macOS 版本在构建验证后确定。
- 第一批终端：优先以 iTerm2 + zsh 作为开发和调试环境，并验证 macOS Terminal；其他终端后续扩展。暂不假定所有终端都能可靠提供光标位置。
- 第一版学习默认只启用候选项排序；发现新选项作为待确认建议，不自动加入默认候选。用户确认后写入个人覆盖层。
- 按会话和命令上下文学习选项，不学习自由文本参数、路径、环境变量值或完整命令行。
- 不提供联网更新功能。规则版本通过用户手动安装新的完整应用包更新；运行时不检查更新。

### 3.1 语言与组件边界（2026-11-10）

- 核心、命令行代理、shell 集成、IPC、规则、排序、学习和构建/盘点工具全部使用 Go（Go 1.27.3）；依赖通过 `vendor/` 固定，构建使用 `-mod=vendor`。
- 不使用 Rust/Cargo 或 Node 作为实现语言；上游 Rust 代码只作为行为、规则格式和终端序列的参考，不进入运行时。
- macOS 候选窗口的 AppKit 交互是唯一允许的非 Go 例外；是否采用需在 T04/T14 验证，不能因此把规则、排序或会话核心迁回 Swift。
- 第三方 Go 依赖必须可审计、版本固定、许可清晰；当前有 `creack/pty`（MIT）和用于本地盘点描述符相对打开的 `golang.org/x/sys`（BSD 3-Clause，另有专利授权声明），移植自 termwiz 的输入解析需保留上游声明。

## 4. 总体结构

```text
终端 + shell 集成
    │ 当前输入、光标位置、当前目录、命令结束状态
    ▼
本地会话代理 ──────► macOS 候选窗口
    │                    │ 选择、取消
    ▼                    ▼
解析器 ─► 规则读取 ─► 候选生成 ─► 排序 ─► 回写 shell
            │             │          ▲
            ▼             ▼          │
       随包基础规则   受限本地数据源   本地学习库
            ▲                        │
            └──── 个人覆盖规则 ◄─────┘
```

- **shell 集成与会话代理**：跟踪 shell 当前输入、光标和命令执行状态，通过本地 IPC 与桌面进程通信；按终端能力获取窗口和光标位置。必须检查原开源实现的 PTY 包装和 shell hooks，不能假设单个 shell hook 足够。
- **解析器**：识别当前命令、子命令、已使用选项和当前 token；返回明确的解析状态，不得将解析不确定性当成确定的命令上下文。
- **规则管理器**：优先读取安装包内基础规则，叠加用户确认的个人覆盖规则。规则按命令懒加载，并可缓存于进程内；无远程回退。
- **候选生成器**：处理静态选项、子命令和受限的文件/目录等本地来源。
- **排序器与学习器**：将基础相关性、近期频率和确认过的覆盖规则组合；排序失败时退回基础排序。
- **界面**：独立窗口显示候选与说明；快捷键可以配置，焦点变化或光标定位失败时隐藏窗口，不能误向其他应用插入文本。
- **管理窗口**（当前实现）：同一 `.app` 内的 `oc-app` 默认以 UIElement 后台运行，通过菜单栏打开主窗口和查看学习指标；主窗口展示概览、学习记录和 agent 日志，学习可开关/清除，日志可刷新/清空。主窗口打开时显示 Dock 图标，关闭后回到后台；菜单栏常驻可在设置中关闭。候选窗口 `oc-window` 是独立的 accessory 进程，不出现在 Dock。

本地 IPC 应使用用户私有目录下的 Unix domain socket 或平台等价机制，限制文件权限并校验连接方；网络 socket 不是必需组件。

## 5. 完全离线的边界

### 5.1 规则必须是可执行资源的安全边界

原 Fig/Q 规则允许 JavaScript、动态生成器和运行外部命令。**只把这些 JS 打进安装包，不足以保证离线**：规则或子进程仍可能访问网络。当前版本为了复刻 Kiro 的 generator 行为，安装了 Node runtime 并执行规则声明的命令与 JavaScript；因此“应用不联网”只描述应用自身，不约束 generator 子进程。

优先盘点开发机上已安装的 Kiro CLI 可获取的补全规则和缓存，尽可能导出本地可用的规则，并记录来源、格式和覆盖范围；不能假定本机已包含所有规则。本机获取的规则不等于已获重新分发许可，打包发布前仍需核查。

构建阶段把静态子命令、选项、参数说明和 generator 元数据导出为 JSON；原始 spec 模块随包加密，运行时按需交给 Node 执行。静态包和 spec 包使用 AES-GCM，密钥嵌在应用内，因此防的是误改/随手替换，不是有能力分析二进制的攻击者。

运行时 generator 会按规则声明的 argv 执行本地程序，支持脚本、文件 template、JavaScript custom、postProcess、cache、trigger 和 fuzzy 过滤。runner 仍限制超时、输出大小和候选数，但不提供网络隔离或命令白名单；规则来源应作为信任边界。

### 5.2 防线与限制

- 移除网络客户端、云规则协议、账号与遥测路径；不加载远程字体、图标或资源。
- 应用自身不创建网络连接；generator 子进程可能访问网络。构建依赖下载发生在开发/发布阶段，不属于用户运行时。
- 如果进程架构、系统框架或未来 provider 仍具有联网能力，需要验证并采用适当 OS 级限制。macOS 沙盒、签名及辅助功能权限的组合可行性是首个技术验证项，不预先保证实现方式。
- 离线验收在干净虚拟机/测试账户中执行，使用系统级网络观察和阻断；不以“源码未发现请求”作为唯一证据。无法覆盖到的系统进程和测试限制应在报告中注明。

## 6. 规则数据与更新

### 6.1 数据分层

1. **基础规则**：只读、随版本发布。包含命令 ID、别名、子命令树、选项、参数类型、描述、来源和许可信息。
2. **用户覆盖**：用户确认的添加、隐藏、别名或说明修正；始终覆盖基础层，独立保存，不因升级丢失。
3. **学习状态**：上下文中的候选使用次数、时间和待确认建议。与规则分离，丢失时不影响基础补全。

示例（仅示意，实际 schema 需版本化）：

```json
{
  "schemaVersion": 1,
  "command": "mytool",
  "subcommands": [{
    "name": "deploy",
    "options": [{"name": "--region", "description": "Deployment region"}]
  }],
  "source": {"repository": "example", "revision": "<commit>", "license": "MIT"}
}
```

### 6.2 构建与安装

构建时固定来源仓库与提交，保存许可证、转换器版本、规则清单及哈希；生成可复现的规则包。安装器包含应用、规则包与许可文件。启动时检查 schema 兼容性与规则包完整性；失败则明确提示，禁止请求网络补救。

用户手动安装新版本时先备份个人数据，迁移 schema 并保留旧应用/规则包的回滚路径；基础规则新增与个人覆盖冲突时，以个人覆盖优先并在管理界面标记。规则包更新不应重置学习数据。受签名和公证约束的最终打包方案待技术验证。

## 7. 学习机制

### 7.1 排序学习

上下文键由已解析的命令 ID、子命令路径、当前参数槽位和候选类型组成；不包含自由文本、工作目录或完整命令行。只统计用户**明确选择并插入**的候选；命令执行成功可以作为另一个弱信号，不能作为正确性的证明。

示例排序：

```text
score = base_score + 0.15 * min(log(1 + selected_count), 3)
                   + 0.10 * recency_score
                   + 0.50 * correction_confidence
                   + 0.10 * correction_recency
                   - correction_penalty
```

先做前缀/语法匹配，再对候选打分；`recency_score` 在 0 到 1 之间并随时间衰减。个人纠正用 Wilson 置信下限，并在至少 3 次、跨 2 个日期后作为额外候选注入；被反复纠正的静态候选在当前上下文降权。权重仅为初始参数，需用可重复测试和实际体验调节；基础规则的禁用/冲突约束优先于学习分数。未命中或解析不确定时使用基础排序。

### 7.2 缺失选项发现

当命令解析可靠，用户最终手动输入了某个合法形式的选项名（例如 `--region`），且内置及个人规则都不包含它，可记录一次匿名化观察：`命令 ID + 子命令路径 + 选项名`。同一条命令行的编辑次数只能算一次观察，不记录选项值。默认仅统计白名单命令及选项名；无法排除敏感信息或变量展开的输入直接丢弃。

当同一候选在至少 **3 个不同会话日** 出现，且至少一次退出状态为 0 时，生成一条待确认建议。三个会话日是保守初值，不是统计正确性保证；退出状态 0 也可能掩盖错误。用户可确认加入当前上下文的个人覆盖、忽略或永久屏蔽建议；不自动删除或重写基础规则。对未知命令或解析不明确的输入不产生建议。

### 7.3 修正规则

用户可直接在管理界面为特定命令上下文添加、隐藏或修改候选，并撤销。一个候选被反复跳过不等于错误；系统只能降低其排序或提出建议，不自动删除。软件版本和项目配置不同可能使规则不同，第一版将此视为已知限制，允许用户手工关闭对应覆盖。

## 8. 数据与隐私

学习数据放在 `~/.oc/learning.json`，使用版本化本地存储保存选择记录和个人纠正；目录和文件限制为当前用户可访问，旧版 Application Support 数据首次打开时迁移。设计目标是 SQLite；当前开发实现使用带 schema 版本、原子写入和 0600 权限的 JSON 文件，接口可在后续替换为 SQLite。资源规则和用户数据分别管理，写入使用原子替换，防止异常退出损坏。

- 不保存完整命令行、命令输出或环境变量；个人纠正会保存用户提交的 token，token 本身可能包含路径或敏感值，因此只存本机并支持关闭、清除和导入/导出。
- 默认保留最近 90 天的学习观察；汇总计数同步衰减或过期。具体保留时间可配置。
- 提供暂停学习、删除单个建议、清除某命令数据和清空全部学习数据；删除不影响基础规则。
- 不声称仅靠名称过滤即可识别所有敏感信息。日志默认不包含输入文本或候选名（只含上下文、计数、长度、路径和错误），默认写入 `~/.oc/logs` 并保留 3 天；`OFFLINE_COMPLETE_LOG_TEXT=1` 显式开启文本调试，管理窗口提供日志开关、目录、保留天数、查看和清空入口。

## 9. 交互与容错

- 输入过程中弹出与当前 token 对应的候选；上下选择、确认插入、Esc 关闭。原样输入和正常执行始终可用。
- 窗口定位失败、权限缺失、shell 未连接、规则损坏或进程异常时关闭补全并显示可诊断状态，不阻塞终端。
- 安装时说明需要的辅助功能权限及其用途。退出或卸载时只移除由本应用添加且可识别的 shell 集成；先检测已有 Kiro 集成，不自动删除用户配置。
- 管理页包含：运行状态、支持的终端/shell、规则包版本、学习开关、待确认建议、个人覆盖和清除数据。无账号与更新入口。

## 10. 实施顺序与验收

### 阶段 0：可行性验证

- 完整检出指定的开源提交，确认许可证、构建依赖和第三方资源；确认上游代码只作行为参考，不引入 Rust 构建链。用 Go 工具链验证本项目的 Apple Silicon/Intel 构建。
- 列出桌面窗口、PTY/shell、IPC、规则加载、账户及网络模块的依赖图；确认目标终端定位与插入可用。
- 盘点并提取本机 Kiro CLI 可获取的规则和缓存，记录可导出数量、格式、来源和缺失项。
- 对声明式规则转换抽样测量覆盖率，列出无法转换的动态规则与替代方案。

### 阶段 1：离线基础版

- 去除所有云端路径，接入本地规则包；完成 zsh 和目标终端的补全、插入、启停、卸载。
- 在断网且从未联网启动的干净环境中安装并测试 `git`、`npm`、`docker` 等静态规则与本地文件候选。
- 监控并阻断应用和其子进程网络连接；分别覆盖首次启动、首次加载规则、输入、插入、设置、重启和卸载。验证没有尝试连接；记录测试工具、进程树和覆盖范围。
- 在缺权限、规则损坏、终端重启和应用崩溃时确认 shell 可继续正常工作。

### 阶段 2：个人学习

- 验证排序按上下文隔离、重启后保留、按期衰减；禁用和清除后立即生效。
- 验证重复编辑不会重复计数；符合阈值后出现建议，确认/忽略/撤销均可用；错误建议不会自动写入基础规则。
- 测试敏感输入、变量、路径和参数值不进入持久化记录或默认日志；模拟数据库故障并验证基础补全可降级运行。

### 阶段 3：发布

- 形成规则来源及许可证清单、构建和签名流程、离线安装说明、兼容矩阵、升级/回滚与卸载说明。
- 对每个支持的 macOS/终端/shell 组合执行人工回归；明确已知不支持的动态规则和辅助功能限制。

## 11. 需要实现者确认的问题

1. 确定最低 macOS 版本，以及与 Kiro 并存时由哪个进程接管补全。
2. Go 重写需要覆盖哪些上游终端行为；哪些终端兼容细节只能通过真机验证。
3. 规则来源及各项许可；声明式转换对常用命令的覆盖率与缺失动态功能。
4. macOS 辅助功能权限、沙盒、代码签名、公证与网络隔离组合的可行性。
5. 缺失选项识别是否在不存储参数值的前提下可可靠关联命令上下文与退出状态；不能可靠判断时不学习。
